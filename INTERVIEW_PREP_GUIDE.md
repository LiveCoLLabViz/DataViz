# PART I — PROJECT UNDERSTANDING

## 1. Project Summary

**What it is (the vision):** LiveCollab is a collaborative data-visualization / lightweight BI tool. A user signs up, creates a *workspace*, invites members, uploads a dataset (CSV/JSON/XLS/XLSX), drags fields onto chart "wells" to build charts, arranges them on a dashboard canvas, and — in theory — collaborates in real time via chat and live dashboard updates, with version history.

**What it actually is (the code):**
- **[CODE]** A React SPA (`live collab/`) with a genuinely rich UI: drag-and-drop field wells, a draggable/resizable chart canvas, Redux-managed dashboard state with undo/redo, PNG export, a chart-building panel, and a real client-side aggregation engine (`buildChartData`).
- **[CODE]** An Express + MongoDB backend (`server/`) with Mongoose models for users, workspaces, datasets, dashboards, charts, messages; REST controllers for each; file upload via Multer + Cloudinary; CSV/Excel parsing; JWT + Google OAuth login; and a Socket.IO chat server.
- **[GAP]** The two are **not integrated**: the frontend points at the wrong port and double-prefixes `/api`, charts are never sent to the backend, no REST route enforces authentication, and the socket auth middleware is commented out.

**One-sentence version for the interview:** *"A MERN + Socket.IO collaborative dashboarding prototype — real models, real UI, real client-side charting — where the auth enforcement and client/server integration are still stubbed."*

**Stack (from `package.json` files):**
- Backend: Node + Express 5, Mongoose/MongoDB, Socket.IO 4, `jsonwebtoken`, `bcrypt`, `multer`, `cloudinary`, `passport` + `passport-google-oauth20`, `papaparse`, `xlsx`, `express-session` (declared, **unused**), `cors`, `dotenv`.
- Frontend: React 19, Vite, Redux Toolkit + react-redux, react-router-dom 7, Recharts, socket.io-client, react-dnd (+ html5 backend), react-draggable, re-resizable, html-to-image, framer-motion, react-hot-toast, Tailwind 4.

**Key architectural truths to state plainly:**
- It is a **client-heavy** architecture: the actual chart computation (group-by + aggregate) happens in the browser in `DashboardCanvas.jsx::buildChartData`, **not** on the server. The server mostly stores blobs and metadata.
- The backend is a **thin CRUD + file-parse layer**. There is no service/repository separation — controllers talk to Mongoose directly.
- Real-time is a **separate, parallel channel** (Socket.IO) that shares the HTTP server (`initializeSocket(app)` wraps the Express app in `http.createServer`) but **does not share auth** with the REST layer.
- There is **no API gateway, no caching layer, no queue, no worker** — everything is synchronous in the request thread, including file parsing.

## 3. Complete Request / Data Flow (trace these end-to-end)

### 3a. Signup / Login (email+password)
1. **[CODE]** Frontend `SignIn.jsx` — note its own comment: *"frontend-only sign-in form… placeholder handlers only."* The real call would go through `authService`.
2. **[CODE]** Backend `POST /register` (UserRoutes mounted at **root**, so the path is `/register`, **not** `/api/auth/register`). `auth.controller.js::register` hashes the password with bcrypt, saves the user, and **returns the full user document including the password hash** in the JSON response — an information-disclosure bug.
3. **[CODE]** `POST /login` → compares bcrypt → `generateToken(userId)` → `jwt.sign({ userId }, JWT_SECRET, { expiresIn: "7d" })`.
4. **[GAP]** Frontend `constants.js` builds the login URL from `API_BASE_URL = http://localhost:8000/api` **and** hardcodes `/api/...` on the endpoint → request goes to `http://localhost:8000/api/api/...` on **port 8000**, but the server listens on **PORT (5000)** and auth is at **root**. So as written, login cannot reach the server.

### 3b. Google OAuth
1. **[CODE]** `/google` → Passport `GoogleStrategy` (`passportconfig.js`). On first login it creates a user with **`password: profile.id`** — the Google ID stored as a *plaintext* password (no bcrypt hook on this path).
2. **[CODE]** `/google/callback` → `handleGoogleCallback` signs a token with payload **`{ id, email }`** and **`expiresIn: "1h"`** — different key (`id` vs `userId`) and different expiry than the email/password path. It sets an httpOnly cookie **and** redirects to the client with **`?token=<jwt>` in the URL**.
3. **[TRAP]** Because Google tokens carry `id` but `authMIddleware.js` reads `decoded.userId`, and `socketAuth.js` reads `decoded.id`, the two token shapes are mutually incompatible with the two consumers. (See Section 10.)

### 3c. Dataset upload
1. **[CODE]** `POST /api/dataset/...` → Multer (`cloudinary.config.js`) saves to disk `uploads/tmp`, `limits.fileSize = 5MB`, `fileFilter` allows by **extension** (`.csv/.json/.xlsx/.xls`) — not MIME, so a renamed file passes.
2. **[CODE]** `datasetController.js` parses via `parsecsv.js` (PapaParse) or `parseexcel.js` (xlsx). **Both use blocking `fs.readFileSync`** — the event loop stalls for the whole parse.
3. **[CODE]** Rows are **silently truncated at `MAX_ROWS = 5000`**. A 200k-row upload becomes 5k with no warning to the user.
4. **[CODE]** The full parsed rows are stored in Mongo as `ParsedData: [Object]` on the Dataset doc → risks the **16 MB BSON document limit** for wide/long data.
5. **[CODE]** The file is also pushed to Cloudinary; `filePath` stores the Cloudinary **`secure_url`**.
6. **[BUG]** `deleteDataset` calls `cloudinary.uploader.destroy(...)` derived from the `secure_url`, but `destroy()` needs the **`public_id`** → remote deletion silently fails and orphans the asset.

### 3d. Build a chart (the important one)
1. **[CODE]** User drags a field; `useDragDropField` + `chartSlice` track wells (rows/columns/filters/metric), chart type, color, aggregation, sort.
2. **[CODE]** `DataPanel.jsx::handleCreateChart` calls **local** Redux `addChartToActiveDashboard` and computes data with `buildChartData` — **it never calls the backend.** Charts live only in browser memory.
3. **[CODE]** `DashboardCanvas.jsx::buildChartData({ rows, columns, filters, aggregation, sort })`:
   - Groups rows by `columns[0].name` (the first dimension).
   - Aggregates the measure with **sum / count / min / max / average**, coercing values via `parseFloat(row[yKey]) || 0` (so non-numeric or missing → `0`, silently corrupting sums/averages).
   - Sorts, then **`slice(0, 100)`** (top-100 cap, silent).
   - **Fallback:** if `parsedData` isn't attached to the field, it fabricates mock numbers from the field-name length — meaning a mis-wired chart shows **plausible but fake bars**.
4. **[CODE]** `ChartCard.jsx` renders via Recharts, is draggable (`react-draggable`, grid 20px) and resizable (`re-resizable`), and exports PNG via `html-to-image`.

### 3e. Real-time chat
1. **[CODE]** `SocketProvider` connects with the token when present. Frontend emits events named like `workspace:join` / `chat:message` (`SOCKET_EVENTS` in `constants.js`).
2. **[BUG]** Backend handlers listen for **`joinWorkspace` / `sendMessage`** — names don't match, so messages never route.
3. **[BUG]** `socket.server.js` has **`// io.use(socketAuth);` commented out** → `socket.user` is `undefined` → every handler that reads `socket.user.name` **throws** on the first message.
4. **[BUG]** `chart.controller.js` (misnamed — it's actually a chat-socket registrar) imports `../models/Message.js` (capital M) but the file is `message.js` → **breaks on case-sensitive filesystems (Linux/prod)**, works on your Windows/Mac dev box.
5. **[BUG]** Its `.populate("sender", "name email")` targets model `"User"`, but the model is registered as `"user"` → **MissingSchemaError** at runtime even if you get past the above.

## 5. Database Design

Six Mongoose models. **Know the exact field names and the registration-name bug.**

**`user.js`** — `mongoose.model("user", …)` ← **lowercase**
- `name`, `email` (unique, required), `googleId`, `password` (required), `role` enum `['viewer','admin','editor']` **default `'viewer'`** (this is a **global** role, not per-workspace), timestamps.

**`workspace.js`**
- `name`, `owner` (ref `User`), `members: [ref User]` (**no per-member role, no joinedAt** — contradicts the RBAC described in `server/readme.md`), `createdAt: { type: Date, default: Date.now() }` (**called immediately** — antipattern; should be `Date.now` without parens or rely on timestamps).

**`datasets.js`**
- `OriginalfileName`, `filetype`, `filePath` (required, holds Cloudinary URL), `columns: [String]`, `ParsedData: [Object]` (**entire dataset rows embedded**), `rowCount`. **No `uploadedBy` / `workspace` link** — datasets aren't scoped to an owner or workspace.

**`dashboard.js`**
- `name`, `workspace` (ref `Workspace`), `charts: [ref Chart]`, `versionHistory: [{ savedAt, savedBy (ref User), chartSnapshot: [ref Chart] }]`, timestamps. **No `shareToken` / `isPublic`** (sharing described in docs is absent).

**`Chart.js`** — `mongoose.model('Chart', …)`
- `dashboard` (ref), `datasetId` (ref), `chartType` enum **`['bar','pie','line','histogram']`** (**no scatter/area/donut/heatmap** — but the frontend offers them), `xaxis` (required), `yaxis` (required), optional `aggregation`, `filters: [{ field, operator, value }]`, `config`. **No `lockedBy`/`lockedAt`** → the "soft-locking" in the docs is **NOT IN REPO**.

**`message.js`** — `mongoose.model("Message", …)`
- `workspaceId`, `sender` (ref `User`), `message`, timestamps.

### The population bug (confirmed)
Every model registers Mongoose model names, and every cross-model `ref:` uses **`"User"`** (capital). But the user model is registered as **`"user"`** (lowercase). Mongoose model names are **case-sensitive**. So any `.populate()` on a `User` ref throws `MissingSchemaError: Schema hasn't been registered for model "User"`. The one place this fires today is `chart.controller.js:52` → `.populate("sender", "name email")`.

### Schema design critiques (be ready to volunteer these)
- **Embedding full `ParsedData` in the Dataset doc** — fine for a demo, breaks at scale (16MB cap, whole-doc reads/writes, no partial fetch). Real BI stores rows columnar/external and keeps only schema + a pointer.
- **No indexes declared** beyond `email: unique`. Queries like "dashboards by workspace," "messages by workspaceId" do collection scans.
- **No `datasetId → workspace/owner` link** → impossible to enforce "can this user see this dataset?" server-side.
- **Denormalized chart snapshots that store only ObjectId refs** → version "snapshots" don't actually capture chart config at that point in time (see Section 10).

## 6. Auth & Security (what's actually there vs claimed)

**Implemented [CODE]:**
- Password hashing with bcrypt on register; bcrypt compare on login.
- JWT issuance (`{ userId }`, 7-day) via `generateToken`.
- A working `authMIddleware` that verifies Bearer tokens.
- Google OAuth login via Passport.
- CORS with an origin function + credentials.

**The catch — none of it is enforced:**
- **`authMIddleware` is applied to ZERO routes.** Every REST endpoint is public. `datasetUpload.js` even imports it and then never uses it.
- **User identity comes from the URL.** Controllers read `req.params.userId` / `req.params.workspaceId`. So `GET /api/workspace/<anyUserId>` returns another user's workspaces → textbook **IDOR / broken object-level authorization (BOLA)**.
- **Socket auth is commented out** (`// io.use(socketAuth)`), and even if enabled it reads the wrong token field (`decoded.id`).
- **Google tokens are placed in the redirect URL** (`?token=`) → leaks via browser history, `Referer` headers, and server logs.
- **Register returns the password hash** in the response body.
- **`authMIddleware` logs the token** on failure → tokens land in log aggregation.
- **Google users get `password: profile.id`** stored as plaintext (unhashed).

**Claimed but NOT IN REPO:** per-workspace RBAC (`members[].role`), `roleMiddleware`, share tokens / public dashboards, soft-locking, ownership checks on delete. `server/readme.md` describes all of these; the code has none.

**Bottom line for the interview:** *"The building blocks of auth exist but authorization is effectively absent — no route is protected, and object access is keyed off URL params. I'd treat that as the number-one thing to fix."* Saying this yourself is far stronger than being caught.

## 7. Major Technical Decisions (and how to defend/critique each)

| Decision | Why it's reasonable | The honest critique |
|---|---|---|
| **Client-side aggregation** (`buildChartData` in browser) | Zero server compute; instant re-render on filter change; fine for ≤ a few k rows | Doesn't scale past what fits in browser memory; `slice(0,100)` and `MAX_ROWS=5000` silently cap; duplicated logic if you ever add server export |
| **Embed parsed rows in Mongo** | One doc = whole dataset, simple to fetch | 16MB cap; heavy reads; no columnar access; couples storage to Mongo |
| **JWT (stateless) auth** | No session store; scales horizontally | Can't revoke; 7-day expiry is long; token-in-URL on OAuth path |
| **Socket.IO for real-time** | Rooms per workspace; easy chat/broadcast | Single-node only as written (no Redis adapter); shares no auth with REST |
| **Redux Toolkit for everything** | Predictable state, undo/redo via snapshots | Deep-clone (`JSON.parse(JSON.stringify)`) undo is unbounded and O(state) per action; impure reducer reads `window.innerWidth` |
| **Cloudinary for files** | Offloads storage/CDN | Chosen for images; used here for CSVs (works, but it's a media CDN); delete-by-URL bug |
| **Passport Google OAuth** | Standard, offloads identity | Only login; token/payload inconsistency with the rest of the app |

**The meta-point:** most decisions are *defensible for a prototype*. The weakness isn't the choices, it's the **inconsistent, unfinished execution** (mismatched ports, token shapes, model names, unenforced auth).

## 8. Performance Characteristics

**What's actually true today:**
- **Blocking file parsing.** `fs.readFileSync` + synchronous PapaParse/xlsx run on the event loop. A single large upload **stalls all concurrent requests** on that Node process.
- **Whole-dataset reads.** Fetching a dataset pulls the entire embedded `ParsedData` array over the wire and into memory, every time.
- **Client-side group-by** is O(rows) per chart build, re-run on every well change; capped at 5000 rows in, 100 groups out.
- **Unbounded undo history.** Each dashboard mutation deep-clones the entire dashboard state into a `past[]` array that is never trimmed → memory grows with edits.
- **No caching anywhere** — no HTTP caching headers, no Redis, no memoization of parsed datasets or chart results.
- **No pagination** on list endpoints (workspaces, messages, datasets).

**The interview framing (current → bottleneck → measure → optimize → trade-off):**
- *Current:* synchronous parse in request handler. *Bottleneck:* event-loop block; p99 latency spikes under concurrent uploads. *Measure:* load test concurrent 5MB uploads, watch event-loop lag (`perf_hooks`), Node CPU. *Optimize:* stream-parse (`papaparse` stream / `xlsx` streaming) or move parsing to a worker thread / queue. *Trade-off:* added complexity, eventual-consistency on "dataset ready."
- *Current:* embed rows in Mongo. *Bottleneck:* 16MB cap + huge reads. *Measure:* doc size distribution, read latency. *Optimize:* store rows in object storage / a columnar store, keep schema + rowCount in Mongo. *Trade-off:* two-system consistency, more moving parts.

## 9. Scalability Characteristics

**As written, it is single-node and not horizontally scalable for real-time:**
- **Socket.IO has no Redis adapter** → multiple backend instances can't share rooms; a message emitted on instance A never reaches a user on instance B. (Also, chat is broken today, but this is the scaling ceiling once fixed.)
- **JWT auth is stateless**, so the *REST* layer *could* scale horizontally behind a load balancer — that part is genuinely fine.
- **Local disk temp files** (`uploads/tmp`) tie an in-flight upload to one instance; fine because Cloudinary is the durable store, but the temp files aren't always cleaned up.
- **No queue/worker separation** → CPU-heavy parsing competes with request serving on the same process.
- **Mongo is a single connection with no read replicas / sharding config** and few indexes.

**Staged answer (see Part IV for the full drill):** the honest first sentence is *"Today it runs on one node and the socket layer is the hard blocker to scaling out; the REST layer is stateless and would scale more easily once auth is enforced."*

## IV-4. "What If This Breaks?" (failure-mode readiness)

## IV-5. Staged System Design (rehearse this as a monologue)
1. **Make it actually run:** enforce `authMIddleware` on all mutating routes; derive `userId` from the token; fix the frontend base URL/port and socket event names; unify the token payload; fix the `user`/`User` model name.

3. **Toward 1M users:** move file parsing to a **queue + worker** (BullMQ/SQS); externalize dataset rows to **S3 / columnar store**; add **indexes** (`workspace`, `dashboard`, `workspaceId`); paginate list endpoints; cache parsed results.
4. **Real-time at scale:** add the **Redis Socket.IO adapter**; sticky sessions or a WS-aware LB; persist chat with an ack protocol.
5. **HA / remove SPOFs:** Mongo replica set (+ read replicas), multiple stateless API nodes behind an LB, object storage for durability.
6. **Regional failover:** multi-region Mongo, geo-routing, S3 cross-region replication; accept eventual consistency for non-critical reads.
7. **Consistency for co-editing:** optimistic concurrency (dashboard `version` field, reject stale writes) or CRDT/OT for true simultaneous editing; today it's last-write-wins.
8. **Observability:** metrics (event-loop lag, upload latency, socket connection count), traces across HTTP→worker, alerting; audit logs for access (which also gives you the security trail you currently lack).
