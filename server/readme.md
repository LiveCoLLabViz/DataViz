## 1. Overall Project Workflow

The full application lifecycle—from first visit to a shared, live dashboard—passes through six distinct stages.

---

### Stage 1 – User Onboarding

A new visitor opens the LiveCoLab URL in their browser.
They click **Register** and fill in name, email, and password.
The frontend sends this data to the backend via HTTP POST.
The backend validates the input, hashes the password with **bcrypt**, and creates a User document in MongoDB.
A **JWT (JSON Web Token)** is generated and returned to the client.
The token is stored in `localStorage` in the browser.
The user is automatically redirected to the main dashboard home page.

---

### Stage 2 – Workspace Setup

After login, the user either creates a **new workspace** or joins an existing one via an invite link.
A workspace is a shared project container — everything else (dashboards, datasets, charts) lives inside it.
The creator of the workspace is automatically assigned the **Admin** role.
The Admin can invite teammates by email and assign them roles: **Editor** or **Viewer**.
Every invited member receives an email with a join link (or can be added directly if the admin knows their account).

---

### Stage 3 – Dataset Upload

Inside a workspace, any Admin or Editor can upload a data file (CSV, Excel, or JSON).
The file travels from the browser to the backend via a **multipart HTTP POST** request.
**Multer** receives the file and saves it temporarily in the server's `/uploads` folder.
**PapaParse** (for CSV) or the **xlsx** library (for Excel) parses the file into a structured array of row objects.
This parsed data is stored permanently in MongoDB under the **Datasets collection**.
The frontend receives a list of column names, which it will use when the user sets up chart axes.

---

### Stage 4 – Dashboard and Chart Creation

An Admin or Editor creates a new **Dashboard** inside the workspace.
They pick a dataset and choose a chart type: Bar, Line, Scatter, Pie, or Heatmap.
They map dataset column names to chart axes (e.g., "Month" → X-axis, "Revenue" → Y-axis).
The **Recharts** library renders the chart live in the browser.
Multiple charts can be arranged side by side on the same dashboard canvas.
Every new chart configuration is saved to the **Charts collection** in MongoDB.

---

### Stage 5 – Real-Time Collaboration

A second user opens the same workspace in their own browser tab.
Both users are now connected to the same **Socket.IO room** on the backend server.
Every change made by one user — editing a chart, adding a comment, uploading data — is instantly broadcast to all users in the room.
Nobody needs to refresh their browser; updates arrive in milliseconds.
Users can see each other's avatars and names as **presence indicators** on the shared canvas.

---

### Stage 6 – Sharing and Versioning

A dashboard can be shared externally via a **unique URL** generated by the backend.
Every time the dashboard is saved, a **version snapshot** is recorded in MongoDB.
Users can open the **Version History panel**, preview any earlier state, and restore it with one click.
Admins can control whether the share link is public (anyone can view) or private (workspace members only).

### Layer Breakdown

**Frontend (React + Vite)**
Runs entirely in the browser. Handles routing, UI rendering, chart display, file selection, and all real-time state updates. Talks to the backend over two parallel channels: HTTP for data persistence and WebSocket for live updates.

**Backend (Node.js + Express)**
The central brain of the system. Exposes REST endpoints for all CRUD operations. Hosts the Socket.IO server for real-time messaging. Applies middleware for JWT verification and role-based access control. Handles file uploads using Multer.

**Database (MongoDB Atlas)**
Stores all persistent data: users, workspaces, dashboards, charts, datasets, comments, and messages. Connected to the backend via Mongoose, which provides schema validation and a powerful query interface.

**File Storage**
Uploaded CSV and Excel files are held in the backend's local `/uploads` folder after Multer saves them. The parsed content goes into MongoDB. In a production-grade version, files would be pushed to AWS S3 or similar cloud storage.

**External APIs**
Optional integrations with public REST APIs (e.g., OpenWeatherMap, Alpha Vantage for stocks). The backend or frontend can fetch this live data and feed it into the chart engine like any other dataset.

## 3. Module Interactions

The application is composed of eight core modules that have clearly defined responsibilities and interaction patterns.

```
┌──────────────┐       ┌──────────────┐       ┌───────────────────┐
│  Auth Module │──────▶│  User Module │──────▶│  Workspace Module │
│  JWT/bcrypt  │       │  Profile,    │       │  Members, Roles,  │
│  Hashing     │       │  Settings    │       │  Datasets         │
└──────────────┘       └──────────────┘       └────────┬──────────┘
                                                        │
                                          ┌─────────────▼──────────────┐
                                          │       Dashboard Module      │
                                          │  Create, Edit, Share,       │
                                          │  Version History            │
                                          └──────┬──────────┬──────────┘
                                                 │          │
                                    ┌────────────▼──┐  ┌────▼──────────┐
                                    │ Dataset Module│  │  Chart Module  │
                                    │ Upload, Parse │  │  Config, Axes  │
                                    │ CSV/Excel     │  │  Recharts Render│
                                    └───────────────┘  └────┬──────────┘
                                                            │
                                               ┌────────────▼──────────┐
                                               │   Real-Time Module     │
                                               │   Socket.IO            │
                                               │   Event Bus            │
                                               └────────────┬──────────┘
                                                            │
                                    ┌───────────────────────▼──────────────┐
                                    │        Collaboration Module           │
                                    │  Chat, Comments, Annotations,         │
                                    │  Presence Indicators, Version History │
                                    └──────────────────────────────────────┘
```

**Interaction Rules:**

- The **Auth Module** is a gate. No other module functions without a valid JWT.
- The **Workspace Module** is the container. Every other object (dashboard, dataset, chart) is scoped to a workspace.
- The **Dataset Module** is a prerequisite for the **Chart Module**. A chart cannot exist without a linked dataset.
- The **Real-Time Module** wraps all other modules. Any mutation in Chart, Comment, or Chat is propagated through Socket.IO instantly.
- The **Collaboration Module** depends on both Socket.IO (for live delivery) and MongoDB (for persistence of chat and comments).

## 4. Data Flow Scenarios

### 4.1 – User Registration

```
User fills registration form in browser
         │
         ▼
Frontend performs basic validation
(non-empty fields, valid email format, password length)
         │
         ▼
POST /api/auth/register  →  Express Backend
Body: { name, email, password }
         │
         ▼
Backend checks if email already exists in MongoDB
If yes → 409 Conflict response
If no  → continue
         │
         ▼
bcrypt.hash(password, 10)
Produces a one-way irreversible hash
         │
         ▼
New User document saved to MongoDB
{ name, email, passwordHash, role: 'user', workspaces: [] }
         │
         ▼
JWT signed:  jwt.sign({ userId, email }, JWT_SECRET, { expiresIn: '7d' })
         │
         ▼
Response: { token, user: { id, name, email } }
         │
         ▼
Frontend stores token in localStorage
User is redirected to /dashboard
```

---

### 4.2 – User Login

```
User enters email + password
         │
         ▼
POST /api/auth/login  →  Backend
         │
         ▼
Mongoose: User.findOne({ email })
If not found → 401 Unauthorized
         │
         ▼
bcrypt.compare(enteredPassword, storedHash)
If no match → 401 Unauthorized
         │
         ▼
Match confirmed → Generate JWT → Return to frontend
         │
         ▼
Frontend stores token
Every future API call adds header:
  Authorization: Bearer <token>
         │
         ▼
Backend authMiddleware.js:
  jwt.verify(token, JWT_SECRET)
  Attaches decoded payload to req.user
  Proceeds to route handler
```

---

### 4.3 – CSV / Excel File Upload

```
User selects file → Clicks Upload button
         │
         ▼
Frontend creates FormData object
Appends: file, workspaceId, datasetName
         │
         ▼
POST /api/datasets/upload
Content-Type: multipart/form-data
         │
         ▼

         │

         │

```

         │

         │

         │

         │
         ▼
Simultaneously:
  ① Socket.IO emits 'chart-updated' → { chartId, changes: { colorScheme: 'blue' } }
  ② REST  PATCH /api/charts/:id     → persists change to MongoDB
         │
         ▼
Backend Socket.IO receives 'chart-updated'
Broadcasts to all users in workspace room (except sender)
         │
         ▼
User B receives 'chart-updated' event
React state in User B's browser updates
Recharts re-renders with new color scheme
         │
         ▼
User A clicks "Done Editing"
Frontend emits 'unlock-chart' → { chartId }
Backend clears Chart.lockedBy = null
Backend broadcasts 'chart-unlocked' to room
User B's lock icon disappears → chart is editable again
```

## 5. User Roles & RBAC

The platform uses **Role-Based Access Control (RBAC)** with three levels.

---

### 5.1 – Admin

The Admin is the workspace owner and has unrestricted access.

**Can do everything:**
- Create, rename, and delete the workspace itself
- Invite and remove any member
- Assign and change member roles
- Create, edit, and delete any dashboard or chart in the workspace
- Upload and delete datasets
- Toggle dashboard sharing (public vs. private)
- View and restore any version snapshot
- Delete any comment or chat message

---

### 5.2 – Editor

The Editor is an active contributor who can work on content but cannot manage people.

**Can do:**
- Create and edit dashboards and charts they have access to
- Upload new datasets
- Add, modify, and delete their own charts
- Add annotations and comments to any chart
- Send messages in workspace chat
- Share dashboards via link

**Cannot do:**
- Remove users or change their roles
- Delete the workspace
- Delete another editor's dashboard (unless admin grants permission)

---

### 5.3 – Viewer

The Viewer is a read-only participant brought in to review insights.

**Can do:**
- View all dashboards and charts in the workspace
- Interact with charts (zoom, pan, tooltips)
- Read comments and chat messages
- Add their own comments (if enabled by admin)

**Cannot do:**
- Edit any chart or dashboard
- Upload datasets
- Change any chart configuration

---

### Role Enforcement Flow (Backend)

```
Incoming request → authMiddleware verifies JWT
                         │
                         ▼
                   Decode JWT → get { userId, role }
                   Attach to req.user
                         │
                         ▼
                   roleMiddleware.js checks:
                   if (req.user.role === 'viewer' && action requires 'editor')
                     → return 403 Forbidden
                         │
                         ▼
                   Request proceeds only if role satisfies the route's minimum permission
```

Workspace-level roles are stored in `Workspaces.members[]`. When a request touches a workspace resource, the backend looks up the requesting user's role inside that workspace's member array, not a global role field.

## 6. Dashboard Lifecycle

Every dashboard passes through these seven stages from creation to shared, versioned artifact.

---

### Stage 1 – Create Dashboard

An Admin or Editor clicks **"New Dashboard"** inside a workspace.
They enter a name and optional description.
`POST /api/dashboards` creates a new Dashboard document in MongoDB with an empty `charts[]` array.
The Socket.IO server emits `'dashboard-created'` to the workspace room.
All connected users see the new dashboard appear in their sidebar immediately.

---

### Stage 2 – Upload Dataset

The user opens the Data Library panel and uploads a CSV or Excel file.
The file is parsed, and the dataset record appears in the workspace dataset library.
The user selects this dataset to link it to the dashboard they are building.
The frontend fetches the column names, which populate the axis selector dropdowns.

---

### Stage 3 – Create Chart

The user opens **"Add Chart"**, selects the dataset, picks a chart type, and maps columns to axes.
The chart config is saved to MongoDB and broadcast to all users.
The chart widget appears on the dashboard canvas for everyone in the workspace.

---

### Stage 4 – Edit Chart

A user clicks **"Edit"** on a chart card.
The chart is locked (lock icon visible to others).
The user makes changes: axis labels, chart type, color, filters, annotations.
Each change is synced in real time via Socket.IO and persisted to MongoDB via REST.
The user clicks **"Done"** to release the lock.

---

### Stage 5 – Save Dashboard

The dashboard auto-saves every time a significant change is committed (chart create/edit/delete).
A manual **"Save"** button triggers `PATCH /api/dashboards/:id`.
Each save appends an entry to `versionHistory[]` in the Dashboard document containing a full snapshot of all chart configurations at that moment.

---

### Stage 6 – Share Dashboard

The user clicks **"Share"**.
The backend generates a unique `shareToken` (UUID-like string) and saves it on the Dashboard document.
The shareable URL is: `https://livecolab.vercel.app/share/:shareToken`
Anyone who visits this URL can view the dashboard.
The Admin can toggle sharing off (making the dashboard workspace-private again).

---

### Stage 7 – Version History

The **Version History panel** lists all saved snapshots with timestamp and who saved them.
`GET /api/dashboards/:id/versions` returns the version list.
The user can click any version to preview it.
Clicking **"Restore"** calls `POST /api/dashboards/:id/restore/:versionIndex`.
The backend replaces the current chart configurations with those from the selected snapshot and saves a new version entry noting the restore action.

## 7. MongoDB Collections & Relationships

---

### Users Collection

```
{
  _id:            ObjectId,
  name:           String,
  email:          String  (unique, indexed),
  passwordHash:   String,
  profilePicture: String  (URL),
  workspaces:     [ ObjectId  →  Workspaces ],
  createdAt:      Date,
  updatedAt:      Date
}
```

Stores authentication credentials and workspace memberships. The `workspaces` array contains references to every workspace the user belongs to, for quick lookup on login.

---

### Workspaces Collection

```
{
  _id:         ObjectId,
  name:        String,
  description: String,
  admin:       ObjectId  →  Users,
  members: [
    {
      userId:   ObjectId  →  Users,
      role:     String    ('admin' | 'editor' | 'viewer'),
      joinedAt: Date
    }
  ],
  dashboards:  [ ObjectId  →  Dashboards ],
  datasets:    [ ObjectId  →  Datasets ],
  createdAt:   Date
}
```

The central container document. Everything else belongs to a workspace. Role information is stored per-member inside the workspace, allowing the same user to be an Admin in one workspace and a Viewer in another.

---

### Dashboards Collection

```
{
  _id:         ObjectId,
  name:        String,
  description: String,
  workspaceId: ObjectId  →  Workspaces,
  createdBy:   ObjectId  →  Users,
  charts:      [ ObjectId  →  Charts ],
  shareToken:  String  (unique UUID, for public sharing),
  isPublic:    Boolean,
  versionHistory: [
    {
      savedAt:       Date,
      savedBy:       ObjectId  →  Users,
      chartSnapshot: [ Object ]  ← full chart config at this moment
    }
  ],
  createdAt:   Date,
  updatedAt:   Date
}
```

Represents one dashboard page. The `versionHistory` array is how time-travel versioning works — every save pushes a full snapshot here.

---

### Datasets Collection

```
{
  _id:              ObjectId,
  name:             String,
  workspaceId:      ObjectId  →  Workspaces,
  uploadedBy:       ObjectId  →  Users,
  originalFileName: String,
  fileType:         String   ('csv' | 'xlsx' | 'json'),
  filePath:         String   (server path to raw file),
  columns:          [ String ],  ← column header names
  parsedData:       [ Object ],  ← array of row objects
  rowCount:         Number,
  uploadedAt:       Date
}
```[{1,2,3,4},{5,6,7,8},{},{}]

Stores both the raw file path and the fully parsed data. The `columns` array is what powers the axis selector dropdowns in the chart editor.

---

### Charts Collection

```
{
  _id:         ObjectId,
  dashboardId: ObjectId  →  Dashboards,
  datasetId:   ObjectId  →  Datasets,
  createdBy:   ObjectId  →  Users,
  title:       String,
  chartType:   String   ('bar' | 'line' | 'scatter' | 'pie' | 'heatmap'),
  config: {
    xAxis:        String,
    yAxis:        String,
    colorScheme:  String,
    filters:      [ Object ],
    aggregation:  String,
    showLegend:   Boolean,
    annotations: [
      {
        x:       Number,
        y:       Number,
        text:    String,
        addedBy: ObjectId  →  Users
      }
    ]
  },
  lockedBy:    ObjectId  →  Users  (null when not being edited),
  lockedAt:    Date,
  createdAt:   Date,
  updatedAt:   Date
}
```

Stores the full configuration of a single chart. The `lockedBy` field implements the soft-locking conflict strategy. Annotations are stored directly inside the chart config.

---

### Comments Collection

```
{
  _id:         ObjectId,
  dashboardId: ObjectId  →  Dashboards,
  chartId:     ObjectId  →  Charts  (optional — null if dashboard-level comment),
  userId:      ObjectId  →  Users,
  text:        String,
  timestamp:   Date,
  resolved:    Boolean
}
```

Supports both dashboard-level discussion threads and chart-specific pinned comments.

---

### ChatMessages Collection

```
{
  _id:         ObjectId,
  workspaceId: ObjectId  →  Workspaces,
  senderId:    ObjectId  →  Users,
  senderName:  String,
  message:     String,
  timestamp:   Date
}
```

Stores the workspace-level group chat history. Loaded on first open via REST API; new messages arrive in real time via Socket.IO and are also persisted here.

## 8. REST API Design

All routes except authentication and shared dashboard view require a valid JWT in the `Authorization: Bearer <token>` header.

---

### Authentication

| Method | Endpoint | Auth Required | Description |
|--------|----------|---------------|-------------|
| POST | `/api/auth/register` | No | Create new user account |

## 9. Socket.IO Events Reference

Socket.IO works on an event-driven model. Think of events as named messages sent between client and server in real time over an always-open WebSocket connection.

---

### Events Emitted by Client → Server

| Event Name | Payload | When Triggered |
|------------|---------|----------------|
| `join-workspace` | `{ workspaceId, userId, userName }` | User opens a workspace page |
| `leave-workspace` | `{ workspaceId, userId }` | User navigates away |
| `chart-created` | `{ chart, dashboardId }` | New chart saved via REST; notify peers |
| `chart-updated` | `{ chartId, changes }` | User modifies chart config |
| `chart-deleted` | `{ chartId, dashboardId }` | User deletes a chart |
| `lock-chart` | `{ chartId, userId }` | User begins editing |
| `unlock-chart` | `{ chartId }` | User finishes editing |
| `annotation-added` | `{ chartId, annotation }` | User pins a note to a chart point |
| `chat-message` | `{ workspaceId, message, senderName }` | User sends a chat message |
| `user-online` | `{ userId, workspaceId }` | Heartbeat ping every 30 seconds |
| `data-uploaded` | `{ datasetId, fileName, workspaceId }` | New dataset ready for use |

---

### Events Broadcast by Server → Clients in Room

| Event Name | Broadcast Target | Payload | Effect on Client |
|------------|-----------------|---------|------------------|
| `user-joined` | Room (except sender) | `{ userId, userName }` | Show join notification; update online list |
| `user-left` | Room | `{ userId, userName }` | Update online user list |
| `chart-created` | Room | `{ chart }` | Render new chart on canvas |
| `chart-updated` | Room (except sender) | `{ chartId, changes }` | Re-render updated chart |
| `chart-deleted` | Room | `{ chartId }` | Remove chart from canvas |
| `chart-locked` | Room | `{ chartId, lockedByName }` | Show lock icon; disable edit button |
| `chart-unlocked` | Room | `{ chartId }` | Remove lock icon; enable edit button |
| `annotation-added` | Room | `{ chartId, annotation }` | Display annotation on the chart |
| `new-chat-message` | Room | `{ message, senderName, timestamp }` | Append message in chat panel |
| `user-presence` | Room | `{ onlineUsers: [] }` | Refresh who is currently online |
| `data-uploaded` | Room | `{ datasetId, fileName }` | Show new dataset in data library |

---

### How Socket.IO Rooms Work

```
Socket.IO Server
│
├── Room: "workspace_AAA"
│       ├── socket of User A
│       ├── socket of User B
│       └── socket of User C
│
└── Room: "workspace_BBB"
        ├── socket of User D
        └── socket of User E

Command:  io.to("workspace_AAA").emit("chart-updated", data)
Result:   User A, B, C all receive it
          User D, E do NOT receive it
```

Each workspace gets its own isolated room identified by the workspace's MongoDB `_id`. This ensures changes in one workspace never leak into another.

## 10. Real-Time Synchronization

### The Synchronization Pipeline

```
User A makes a change (e.g., changes chart title)
         │
         ▼
React state updates locally and immediately
(User A sees the change at once — this is an optimistic update)
         │
         ├─── ① Socket.IO emits 'chart-updated' to server
         │
         └─── ② REST PATCH /api/charts/:id sent to server
                         │
              Both paths reach the backend server
                         │
                         ├─── MongoDB: Chart document updated (from ②)
                         │
                         └─── Socket.IO: Server broadcasts 'chart-updated'
                              to all other sockets in the workspace room
                                       │
                              User B receives the event
                                       │
                              React state in User B's app updates
                                       │
                              Recharts re-renders the chart with new title
```

---

### Key Synchronization Concepts

**Optimistic Updates:** User A's own UI updates the moment they make a change, before waiting for server confirmation. This makes the app feel instant.

**Server as Single Source of Truth:** MongoDB holds the authoritative state. If a network failure causes a save to fail, the client can show an error and prompt the user to try again.

**Presence Heartbeat:** Every 30 seconds, each client emits `user-online`. The server maintains an in-memory map of `{ workspaceId → [activeSockets] }`. If a socket disconnects, Socket.IO fires the `disconnect` event, and the server emits `user-left` to notify the room automatically.

**Reconnection Handling:** Socket.IO has built-in reconnection logic. When a user's connection drops (e.g., network issue) and comes back, the frontend automatically:
1. Reconnects to Socket.IO and re-emits `join-workspace`.
2. Makes a fresh REST API call to fetch the current dashboard state.
This ensures the user catches up on any changes made while they were disconnected.

## 11. Conflict Handling Strategy

**The Problem:** User A and User B both try to edit the same chart at the same moment. Whose change wins? What happens to the other's work?

---

### Strategy A – Soft Locking (Recommended for This Project)

**How it works:**

When User A clicks **"Edit"** on a chart, the client immediately emits `lock-chart` to the server. The server sets `Chart.lockedBy = userId` and `Chart.lockedAt = now` in MongoDB, then broadcasts `chart-locked` to all users in the room.

User B's chart card shows:  🔒 *"Being edited by User A"*  
User B's edit button is **disabled** until the lock is released.

When User A clicks **"Done"**, the client emits `unlock-chart`. The server clears `lockedBy` to `null` and broadcasts `chart-unlocked`. User B's edit button becomes active again.

**Timeout Safety:** If User A closes their browser without clicking "Done", the server's `disconnect` event fires and automatically releases any locks held by that socket. Alternatively, a periodic check can release locks that have been held longer than 2 minutes (using `lockedAt` to calculate staleness).

**Visual UX on Locked Chart:**
```
┌───────────────────────────────────────┐
│  Revenue by Month (Bar Chart)         │
│                                       │
│  🔒 Being edited by Priya             │
│     [Edit button greyed out]          │
└───────────────────────────────────────┘
```

---

### Strategy B – Last-Write-Wins (Simpler Alternative)

Both users can edit simultaneously. Every chart document has an `updatedAt` timestamp. When User B submits a change, the backend compares:

- The `updatedAt` timestamp currently in the database
- The `updatedAt` timestamp that User B had when they last fetched the chart

If the database version is **newer** than what User B had → conflict detected → User B receives a warning:
*"This chart was modified by someone else since you opened it. Saving now will overwrite their changes."*

If no conflict → save proceeds normally.

**Trade-off:** Simple to implement and non-blocking, but one user's work can silently overwrite another's with only a warning.

---

### Decision for Your Project

**Use Soft Locking.** It is more visually demonstrable during a viva, clearly shows understanding of concurrency control, requires minimal extra complexity, and gives a much better collaborative UX. The locking fields (`lockedBy`, `lockedAt`) are already included in the Chart schema described in Section 7.

## 15. Module-by-Module Explanation (Viva-Ready)

---

### Module 1 – Authentication Module

**What it does:** Controls who can enter the system and proves their identity on every request.

**How to explain it:** When a user registers, their password is never stored as plain text. It goes through **bcrypt**, which applies a one-way mathematical transformation (hashing). This hash cannot be reversed. When the user logs in, bcrypt re-hashes what they typed and compares the result. If it matches the stored hash, login succeeds.

The server then issues a **JWT (JSON Web Token)** — a compact, signed string containing `{ userId, email, role }`. The user carries this token in every API request. The server verifies the token's signature using a secret key it keeps. If the token is valid, the request proceeds. If not, it's rejected with a 401 error. This way, no session state needs to be stored on the server.

---

### Module 2 – Workspace Module

**What it does:** Provides the collaborative container that groups users, dashboards, and data.

**How to explain it:** A workspace is like a shared Google Drive folder for a team project. Everything inside it — charts, data, dashboards — belongs to that workspace. Each member of the workspace has a role. The Admin created it and manages membership. Editors do the work. Viewers just observe. All access control decisions are made at the workspace level.

---

### Module 3 – Dataset Module

**What it does:** Handles raw file ingestion, parsing, and storage.

**How to explain it:** A CSV file is just text with commas separating values. **PapaParse** reads this text and converts it into a JavaScript array where each row becomes an object: `{ Month: "Jan", Revenue: 12000 }`. The **xlsx** library does the same for Excel files. Once parsed, this structured data goes into MongoDB. The frontend gets back the column names so the user can assign them to chart axes.

---

### Module 4 – Chart Module

**What it does:** Configures and renders data visualizations.

**How to explain it:** A chart in LiveCoLab is not hardcoded — it is a **configuration object** stored in MongoDB. This config says: use dataset X, put "Month" on the X-axis, put "Revenue" on the Y-axis, render as a bar chart, use blue as the color scheme. The **Recharts** library in the browser reads this config, fetches the corresponding data rows from the dataset, and draws the chart on screen. Any change to the config is a change to a database record, and that change is broadcast to all users instantly.

---

### Module 5 – Real-Time Module (Socket.IO)

**What it does:** Keeps all users synchronized without page refreshes.

**How to explain it:** Normal HTTP is like sending a letter — you ask, the server answers, connection closes. **WebSocket** is like a phone call — it stays open. **Socket.IO** uses WebSocket to let the server push messages to clients at any time, without the client asking.

When User A edits a chart, the change travels to the server, which immediately calls out to everyone else in the workspace room: "Hey, chart 42 just changed." Each client receives this message and updates its own screen. This happens in under a second.

---

### Module 6 – Collaboration Module

**What it does:** Connects users emotionally and functionally to the shared workspace.

**Sub-components:**

**Chat Panel** — A real-time group chat scoped to the workspace. Messages travel via Socket.IO and are also saved to MongoDB so they persist when users disconnect and return.

**Annotations** — Users can click on specific data points in a chart and leave text notes pinned to those coordinates. Annotations are stored inside the chart's config object in MongoDB.

**Presence Indicators** — Each browser's socket sends a heartbeat every 30 seconds. The server tracks active sockets per workspace and broadcasts the online user list. When a socket disconnects, the server emits `user-left` and the display updates.

**Version History** — Every dashboard save appends a full config snapshot to the `versionHistory` array. This is a built-in audit trail and time-machine in one.

---

### Module 7 – Dashboard Module

**What it does:** Provides the visual canvas that holds charts and manages the sharing/versioning lifecycle.

**How to explain it:** A dashboard is like a page in a visual report. It contains multiple chart widgets arranged in a grid. The dashboard document in MongoDB references chart IDs and stores version snapshots. When shared, the backend generates a unique token URL that lets anyone — even without a login — view the current state of that dashboard in read-only mode.

---

### Module 8 – API Integration Module

**What it does:** Allows pulling live, dynamic data from external public APIs instead of only uploaded files.

**How to explain it:** Instead of uploading a CSV manually, a user can type in an API URL (e.g., `https://api.openweathermap.org/data/2.5/forecast?city=Delhi&appid=...`). The backend fetches this URL, extracts the relevant data fields, and passes them to the chart engine exactly like a parsed CSV. This means charts can show live weather, live stock prices, or any JSON-based public data source.

## Final Summary — The Big Picture in Five Lines

**MongoDB** is the permanent memory — everything is stored here.
**Express** is the rulebook — it controls what every user is allowed to do.
**JWT** is the ID card — it proves who you are on every request.
**Socket.IO** is the group broadcast system — it keeps everyone in sync instantly.
**React + Recharts** is the visual layer — it shows users charts and handles their interactions.

When explaining LiveCoLab in a viva, think of the system as three clear layers:

```
┌─────────────────────────────────┐
│  PRESENTATION LAYER             │  React frontend — what users see
├─────────────────────────────────┤
│  LOGIC LAYER                    │  Express + Socket.IO — what controls the rules
├─────────────────────────────────┤
│  DATA LAYER                     │  MongoDB Atlas — what stores everything
└─────────────────────────────────┘
```

Every user action travels down through all three layers. The response travels back up. That round trip — from button click to database and back to screen — is the heartbeat of a full-stack web application.
